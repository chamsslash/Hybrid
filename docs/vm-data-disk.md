# Отдельный диск под данные на сервере

Как на боевой ВМ раскладываются данные, когда под систему отведён небольшой загрузочный
диск, а под всё остальное — второй, большой, смонтированный в `/mnt/data`. Описывает
текущее устройство и то, что нужно проверить перед раскаткой.

Локального стенда это не касается: на машине разработчика диск один, и ничего из
описанного настраивать не нужно.

## Что уезжает на большой диск само

Ключевой факт, который экономит много лишней работы: **kind — это Docker-контейнер.**
Нода кластера живёт целиком внутри файловой системы контейнера, то есть внутри
`data-root` Docker'а. Отдельной настройки «где хранить ресурсы Kubernetes» не существует
— они там же, где Docker.

Поэтому один перенос `data-root` утаскивает на большой диск сразу:

- образы всех трёх сервисов и базовые образы, из которых они собираются;
- кэш BuildKit — а вместе с ним и зависимости Maven: все три Dockerfile многоступенчатые,
  Maven работает внутри контейнера-билдера, `~/.m2` подключён как cache mount. На хосте
  от сборки не остаётся ничего;
- саму ноду кластера: etcd со всеми объектами, образы, загруженные через
  `kind load docker-image`, логи подов;
- данные приложений внутри кластера — Postgres, Kafka, MinIO. Все они на `emptyDir`,
  то есть лежат в файловой системе ноды.

Настраивается это в `/etc/docker/daemon.json` (`data-root`) и, для containerd, в его
`config.toml` (`root`).

## Что остаётся на загрузочном диске

| Что | Порядок размера | Действие |
|---|---|---|
| Исходники проекта | сотни МБ | клонировать репозиторий в `/mnt/data` |
| `~/.m2` при запуске `mvn` **на хосте** | до нескольких ГБ | перенести, если гоняешь тесты вне Docker |
| `$TMPDIR` при `kind load docker-image` | сотни МБ пиково | ничего — скрипт сам уводит в `/mnt/data/tmp` |
| `~/.kube/config`, конфиг kind, ключи подписи | килобайты | ничего |

Про `~/.m2`: внутри Docker-сборки он не используется вообще, поэтому всплывает только
если запускать Maven напрямую — например, прогнать тесты перед сборкой образов. Проще
всего увести симлинком:

```bash
mv ~/.m2 /mnt/data/m2 && ln -s /mnt/data/m2 ~/.m2
```

Про `TMPDIR`: `kind load docker-image` перекладывает образы в ноду через промежуточный
tar во временном каталоге. Три образа с JRE — это сотни мегабайт разом, и на небольшом
загрузочном диске оно упирается в место ровно посередине раскатки.

**Делать при этом ничего не нужно.** `deploy-kind.sh` сам выбирает временный каталог:
если `/mnt/data` существует и доступен на запись, он берёт `/mnt/data/tmp`, иначе
остаётся на `/tmp`. То есть на сервере временные файлы едут на большой диск по умолчанию,
а на машине разработчика, где такого каталога нет, поведение прежнее. Скрипт печатает
выбранный путь строкой `▶ временные файлы раскатки: …`.

Переопределить можно двумя переменными:

```bash
DATA_DIR=/mnt/other ./deploy-kind.sh   # другой диск с данными
TMPDIR=/var/tmp ./deploy-kind.sh       # явный путь, побеждает всегда
```

`TMPDIR` экспортируется, поэтому его видят и дочерние процессы — `kind` и `mktemp`,
которым он и нужен.

## Гонка при загрузке и как она закрыта

Демоны, которым конфигами сказано хранить данные в `/mnt/data`, обязаны стартовать
**после** того, как туда смонтирован диск. Иначе `containerd` видит `/mnt/data` как
обычный пустой каталог на корневом разделе, создаёт там свою структуру и начинает писать
— а следом на эту точку монтируется настоящий диск и накрывает всё это собой. Данные
оказываются не на том разделе и вдобавок недоступны.

Порядок задаётся зависимостью от юнита монтирования. Править пакетный юнит
`/lib/systemd/system/containerd.service` нельзя: `apt upgrade docker-ce` положит свою
версию поверх, правка исчезнет молча, а всплывёт это не при обновлении, а при следующей
перезагрузке. Поэтому используется drop-in — каталог `<юнит>.d/` в `/etc/systemd/system/`,
который пакетам не принадлежит и приоритетнее `/lib`:

```bash
sudo mkdir -p /etc/systemd/system/containerd.service.d
printf '[Unit]\nRequiresMountsFor=/mnt/data\n' \
  | sudo tee /etc/systemd/system/containerd.service.d/mnt-data.conf
sudo systemctl daemon-reload
```

То же самое для `docker.service.d/`. Имя файла произвольное, значение имеет только
расширение `.conf`. `daemon-reload` обязателен: без него файл лежит на диске, а systemd
продолжает работать с разобранным юнитом из памяти.

`RequiresMountsFor=` — директива-макрос: получает путь, сама находит покрывающий его юнит
монтирования и вешает на него **две** зависимости, каждая из которых нужна:

- `After=mnt-data.mount` — про порядок: демон не стартует, пока монтирование не
  завершилось. Это и лечит гонку выше.
- `Requires=mnt-data.mount` — про необходимость: если монтирование провалилось, демон не
  запускается вовсе. С одним только `After=` systemd дождался бы попытки, увидел провал —
  и всё равно запустил бы демон на пустом месте.

Те же две строки можно было написать руками. `RequiresMountsFor=` выбран потому, что
оперирует путём, а не именем юнита: не нужно выводить экранированное имя
(`/mnt/data` → `mnt-data.mount`), и при переименовании точки монтирования в `fstab`
директива подхватит новый юнит без правок.

Цепочка целиком:

```
/etc/fstab
   └─ systemd-fstab-generator → mnt-data.mount
        └─ RequiresMountsFor=/mnt/data (drop-in) → Requires= + After=
             ├─ containerd.service → root      = /mnt/data/containerd  (config.toml)
             └─ docker.service     → data-root = /mnt/data/docker      (daemon.json)
```

Конфиги демонов отвечают на вопрос «где лежат данные», drop-in — на вопрос «когда можно
начинать с ними работать». Настроить только первое — это и есть исходная гонка: пути
правильные, а в момент старта по ним ещё ничего нет.

## Проверка

```bash
# диск смонтирован и это действительно он, а не корневой раздел
df -h /mnt/data

# зависимости доехали в эффективный юнит
systemctl show containerd -p Requires -p After | tr ' ' '\n' | grep mnt-data
systemctl cat containerd | tail -3

# Docker реально пишет на большой диск
docker info --format '{{.DockerRootDir}}'

# после раскатки: нода кластера весит там же
sudo du -sh /mnt/data/docker
```

Самая полезная пара — после перезагрузки. Если `DockerRootDir` указывает в `/mnt/data`, а
`df` показывает по этому пути корневой раздел, значит монтирование не приехало и данные
снова пишутся не туда.
