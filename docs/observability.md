## Часть 1. Как это вообще работает

### 1.1. Кто кого опрашивает

Главное, что стоит уложить в голову про Prometheus: **он не принимает метрики, он их забирает сам.**
Это pull-модель, и она противоположна привычной push-модели (statsd, Graphite), где приложение
само шлёт цифры в коллектор.

```
                    раз в 15 секунд
   Prometheus  ────── HTTP GET ──────►  под приложения
   (:9090)            /actuator/prometheus     (:8090)
       │                                          │
       │              ◄──── текст ────────────────┘
       │                    (метрики в формате exposition)
       ▼
   TSDB на диске
       │
       │  PromQL-запросы
       ▼
   Grafana (:3000) ──► дашборды
```

Приложение просто держит HTTP-эндпоинт, который на каждый запрос печатает текущие значения
счётчиков текстом. Никакого состояния между скрейпами приложение не хранит — Prometheus сам
запоминает историю.

Следствия, которые важны на практике:

- **Prometheus обязан уметь найти поды.** Отсюда service discovery и вся возня с RBAC ниже.
- **Приложение не знает, что его мониторят.** Упал Prometheus — приложению всё равно.
- **Метрика, которую никто не скрейпил, не существует.** Если под прожил 10 секунд между скрейпами,
  его метрик в базе не будет вовсе.
- **`up` — бесплатный сигнал.** Prometheus сам записывает `up{job=...} = 1|0` для каждой цели по
  результату скрейпа. Инструментация для этого не нужна: это буквально «удалось ли забрать метрики».

### 1.2. Формат экспозиции

То, что отдаёт эндпоинт, выглядит так (реальная строка из нашего HTTPService):

```
# HELP http_server_requests_seconds
# TYPE http_server_requests_seconds summary
http_server_requests_seconds_count{method="POST",outcome="SUCCESS",status="200",uri="/exchangeTokens",} 3.0
http_server_requests_seconds_sum{method="POST",outcome="SUCCESS",status="200",uri="/exchangeTokens",} 0.412
```

Разбор:

- `http_server_requests_seconds` — **имя семейства метрик** (metric family).
- `{method="POST", uri="/exchangeTokens", ...}` — **лейблы**. Каждая уникальная комбинация лейблов —
  это отдельный **временной ряд** (time series). Именно из-за лейблов появляется понятие
  *кардинальности*: добавил лейбл с сотней значений — получил в сто раз больше рядов.
- `_count` / `_sum` — суффиксы, порождаемые типом метрики.

### 1.3. Четыре типа метрик, и почему разница критична

| Тип | Что это | Что порождает в экспозиции |
|---|---|---|
| **Counter** | Только растёт (или сбрасывается в 0 при рестарте) | `имя_total` |
| **Gauge** | Может расти и падать: температура, размер пула | `имя` |
| **Summary** | Таймер, считающий count и sum, иногда квантили — **посчитанные в приложении** | `_count`, `_sum`, `_max` |
| **Histogram** | Таймер, раскладывающий наблюдения по **бакетам** | `_count`, `_sum`, `_bucket{le="..."}` |

**Практическая разница между Summary и Histogram — та, на которой у нас всё и споткнулось.**

`histogram_quantile()` в PromQL умеет считать перцентили **только по бакетам**. Бакеты бывают
только у Histogram. Значит:

- Метрика — Histogram → можно спросить «а какой p95 у этого эндпоинта, агрегированно по всем подам».
- Метрика — Summary → **нельзя**. Доступны только средняя (`rate(_sum) / rate(_count)`) и `_max`.

Почему так: квантиль нельзя усреднить. Если под A даёт p95 = 100ms, а под B — p95 = 200ms, то p95
по обоим подам **не равен 150ms** и вообще не вычислим из этих двух чисел. Histogram обходит это тем,
что хранит сырое распределение по корзинам, а корзины складываются между подами честно.

В нашем скрейпе:

- `http_server_requests_seconds` — **summary** (бакетов нет) → p95 по HTTP сегодня недоступен.
- `grpc_client_processing_duration_seconds` (от gRPC-стартера) — **summary** → та же беда.
- `grpc_call_duration_seconds` (наш собственный, `HTTPService/.../Metrics/GrpcRequestsMetric.java`) —
  **histogram** → перцентили считаются уже сейчас.

Лечится включением гистограмм в конфиге Micrometer (см. §3.3), но за это платят кардинальностью:
каждый бакет — отдельный ряд на каждый `uri`.

### 1.4. Micrometer и actuator: кто что делает

Легко перепутать три вещи:

- **Micrometer** — библиотека-фасад для метрик. Вы пишете `Counter.builder("...").register(registry)`,
  она хранит значения в памяти. Аналог SLF4J, только для метрик.
- **`micrometer-registry-prometheus`** — конкретная реализация реестра, умеющая напечатать
  накопленное в prometheus-формате.
- **`spring-boot-starter-actuator`** — то, что вешает HTTP-эндпоинт `/actuator/prometheus`,
  по которому этот текст можно забрать, плюс `/actuator/health` и прочее.

Нужны все три. У нас в HTTPService были все три, а в AuthService и MessegerParody — ни одной.

Отдельно: **Spring Boot автоматически инструментирует всё, до чего дотянется.** Появился actuator —
и вы бесплатно получаете `http_server_requests`, `jvm_*`, `kafka_*`, `logback_events`,
`spring_security_*`. Это удобно ровно до момента, когда полезных метрик оказывается 4 семейства
из 317 (см. §2.2).

## Часть 2. Что было сломано у нас

### 2.1. Связка существовала и не работала

`Helm/templates/prometheus.yaml` и `grafana.yaml` рендерились, поды крутились — и ничего не делали.
Четыре независимые поломки:

**(а) Нет RBAC — самая тяжёлая, и её не было в тикете.**

Конфиг Prometheus использует `kubernetes_sd_configs: role: pod` — то есть просит Kubernetes API
перечислить поды. Деплоймент при этом бежал под ServiceAccount `default`, у которого права
`list pods` нет. Ни ServiceAccount, ни Role, ни ClusterRole в `Helm/templates/` не существовало.

Коварство в том, что это **тихая** поломка: Prometheus стартует, UI открывается, целей просто ноль.
Легко принять за «аннотации не проставлены».

**(б) Нет аннотаций `prometheus.io/scrape`** ни на одном pod-шаблоне приложений.
Правило `keep` по этой аннотации отбрасывало всё. Это единственное, что было в тикете.

**(в) Нет тома под `--storage.tsdb.path=/prometheus`.** Смонтирован только ConfigMap с конфигом.
Рестарт пода — история стёрта.

**(г) Grafana пустая.** Ни datasource, ни дашбордов. Из окружения задан только админ-пароль.

Плюс оба образа — `:latest`.

### 2.2. Шум: 317 семейств, из них полезных — единицы

Замер живого скрейпа `httpservice:8080/actuator/prometheus`: **317 семейств метрик, 1295 сэмплов.**

| Префикс | Семейств | Комментарий |
|---|---|---|
| `kafka_*` | **204 (64%)** | Внутренности клиента Kafka |
| `spring_security_*` | 42 | Из них 30 — таймер на **каждый фильтр** security-цепочки по отдельности |
| `jvm_*` | 25 | |
| `executor_*`, `grpc_*` | по 7 | |
| `tomcat_*` | 6 | |
| `lettuce_*`, `http_server*` | по 4 | |

`http_server_requests` — четыре семейства, погребённые под двумя сотнями внутренностей Kafka-клиента.
Вот это и есть «собираем на все случаи жизни».

Но важная тонкость: **среди этих 204 kafka-метрик сидят три самые ценные для нас** —
`kafka_consumer_fetch_manager_records_lag`, `records_consumed_total`, `kafka_producer_record_error_total`.
Поэтому нельзя просто выкинуть префикс целиком; нужен кураторский отбор.

### 2.3. Утечка: /actuator/prometheus смотрел в интернет

Ingress содержит правило `path: / (Prefix) → httpservice:8080` — весь порт 8080 публичен.
А эндпоинт актуатора был намеренно выведен из-под аутентификации:

- `MvcSecurityConfig.java:57` — `web.ignoring().requestMatchers("/actuator/prometheus")`
- `MvcJwtAuthFilter.java:53`, `ReactiveHybridAuthFilter.java:32` — `/actuator/**` в публичных путях

Проверено живьём:

```
$ curl -o /dev/null -w '%{http_code}\n' http://myapp.localtest.me/actuator/prometheus
200
```

Полный дамп метрик кому угодно, без аутентификации: имена всех URI приложения, версия JVM,
имена Kafka-топиков, бизнес-счётчики, uptime. Не катастрофа, но выдача карты внутреннего устройства.

Сделано это было не по глупости, а как **вынужденный костыль**: на этот же эндпоинт завязана
`readinessProbe` (`Helm/charts/httpservice/templates/deployment.yaml:42`), потому что
`/actuator/health` закрыт Security и отвечает 302. Комментарий в чарте это признаёт прямым текстом.

**Урок, который стоит забрать:** костыль, поставленный ради пробы, стал дырой в периметре.
Разделение портов (§3.1) снимает оба вопроса одним движением.

## Часть 3. Принятые решения и обоснования

### 3.1. Management-порт отдельно от бизнес-порта

Ключевое решение всей работы.

| Сервис | Бизнес-порт | Management-порт |
|---|---|---|
| HTTPService | 8080 (за ingress) | **8090** |
| AuthService | 8081 (за ingress) + gRPC 9092 | **8090** |
| MessegerParody | HTTP нет + gRPC 9091 | **8082** (весь порт под актуатор) |

Почему это решает проблему §2.3: если актуатор слушает **не тот порт**, который смотрит в ingress,
то никакие исключения в Spring Security не нужны — эндпоинт физически недостижим снаружи.
Prometheus ходит по pod IP внутри кластера, ingress туда не маршрутизирует.

Это общий принцип, не наша выдумка: management-интерфейс отделяют от пользовательского именно
потому, что у них разные модели доступа. У пользовательского — аутентификация и публичность,
у management — сетевая изоляция.

8090 одинаковый у двух сервисов намеренно: разные поды, конфликта нет, зато аннотации и конфиг
Prometheus получаются однотипными.

**Побочный выигрыш:** можно включить `management.endpoint.health.probes.enabled: true` и перевести
`readinessProbe` на `/actuator/health/readiness`. Она не под security-цепочкой (другой порт),
отвечает 200 без исключений, и — в отличие от `/actuator/prometheus` — действительно означает
«Spring поднял контекст», а не «процесс отвечает по HTTP». Заодно пробы появляются у AuthService
и MessegerParody, где их не было вовсе.

**Порядок обязателен:** снятие `/actuator/**` с публичных путей и перенос пробы делаются **одним
шагом**. Разнесёшь — получишь окно, где проба бьётся в закрытый эндпоинт и под не поднимается.

### 3.2. MessegerParody: сервис без HTTP-сервера

Особый случай. В `MessegerParody/pom.xml` нет ни `spring-boot-starter-web`, ни `webflux` — это
чистый gRPC + Kafka + R2DBC сервис. `server.port: 8082` в его `application.yml` — мёртвая настройка.
Проверено: `wget http://messegerparody:8082/...` из кластера → exit 4, соединения нет.
При этом Service объявляет порт `http: 8082`, ведущий в никуда.

Значит, чтобы отдать `/actuator/prometheus`, надо **добавить HTTP-сервер, которого нет**.
Берём `spring-boot-starter-webflux` (сервис реактивный, R2DBC — логично не тащить сервлетный стек).

**Риск, который надо держать в голове:** это меняет `WebApplicationType` приложения с `NONE`
на `REACTIVE`. Spring начнёт поднимать Netty там, где раньше не поднимал ничего. Порядок старта
gRPC-сервера и Kafka-консьюмера теоретически не меняется, но проверяется живьём, а не на веру:
gRPC на 9091 отвечает через `grpcurl`, консьюмер читает топик.

Альтернатива, которая рассматривалась и отклонена: не трогать сервис вовсе, а смотреть на него
снаружи (kafka-exporter для лага, postgres-exporter для БД). Отклонена потому, что внутри сервиса
остаётся слепая зона — не видно ни почему сообщение ушло в DLT, ни где встала запись в БД,
а это ровно конец пайплайна сообщений, где чаще всего и ломается.

### 3.3. Гистограммы: перцентили в обмен на кардинальность

Из §1.3: p95 по HTTP сегодня недоступен, потому что метрика — summary. Включаем гистограммы:

```yaml
management:
  metrics:
    distribution:
      percentiles-histogram:
        "[http.server.requests]": true
      minimum-expected-value:
        "[http.server.requests]": 10ms
      maximum-expected-value:
        "[http.server.requests]": 10s
```

**Границы заданы явно, и это не косметика.** По умолчанию Micrometer раскладывает наблюдения по
десяткам бакетов, покрывающих диапазон от микросекунд до минут. Каждый бакет — отдельный временной
ряд, и умножается он на каждое значение `uri`. Явные границы 10ms–10s оставляют точность там,
где она нужна для веб-запросов, и режут хвосты, которые всё равно никто не смотрит.

Откат, если ряды всё-таки разлетятся: выключить `percentiles-histogram`, вернуться к средней.

### 3.4. Где резать шум: в Prometheus, а не в приложении

Два места, где можно отфильтровать лишние метрики:

| | В приложении (`MeterFilter`, `management.metrics.enable.*`) | В Prometheus (`metric_relabel_configs`) |
|---|---|---|
| Метрика создаётся | нет | да |
| Скрейп-трафик | меньше | тот же |
| Память под реестр | меньше | та же |
| **Вернуть выкинутый сигнал** | **ребилд образа + редеплой** | **`helm upgrade`** |
| Где читается «что мы собираем» | размазано по трём сервисам | один файл |

Выбран Prometheus. Решающий аргумент — предпоследняя строка: сигнал обычно нужно вернуть **именно
в тот момент, когда что-то горит**, и пересобирать Java-образ в этот момент — худшее из возможных.
Экономия трафика на кластере из трёх подов ничего не стоит.

Реализация: список имён держим читаемым в `Helm/values.yaml`, в ConfigMap собираем в регулярку:

```yaml
# values.yaml
prometheus:
  keepMetrics:
    - "http_server_requests_seconds.*"
    - "grpc_(client|server)_.*"
```

```yaml
# в шаблоне ConfigMap
metric_relabel_configs:
  - source_labels: [__name__]
    action: keep
    regex: "{{ join "|" .Values.prometheus.keepMetrics }}"
```

Так вопрос тикета — «какие метрики мы собираем» — становится списком, который читается за минуту.

**Ловушка с якорями.** Prometheus якорит регулярки в relabel-правилах **целиком**: `regex: foo`
разворачивается в `^(?:foo)$`. Это отличается от `grep`, где `foo` нашёл бы подстроку. Практически:

- `http_server_requests_seconds.*` — сработает;
- `http_server_requests` — **не сработает**, потому что реальное имя длиннее и полного совпадения нет;
- `.*kafka.*` — если нужно именно вхождение подстроки, точки-звёздочки пишутся руками.

Альтернация после `join "|"` при этом собирается правильно: обёртка `^(?:a|b|c)$` группирует всё
выражение целиком, а не только последний элемент.

**Отдельно про `*_rate`:** у кафковых метрик почти всегда есть пара `foo_total` и `foo_rate`.
`_rate` — производная, которую Prometheus считает сам через `rate(foo_total[5m])`. Хранить обе —
платить дважды за один сигнал. Оставляем `_total`.

### 3.5. RBAC: Role, а не ClusterRole

```yaml
kubernetes_sd_configs:
  - role: pod
    namespaces:
      names: [ hybrid-platform ]
```

плюс ServiceAccount + **Role** (`get, list, watch` на `pods`) + RoleBinding в этом же namespace.

Почему Role: всё приложение живёт в одном namespace, ClusterRole дал бы Prometheus право читать
поды всего кластера — прав больше, чем задача требует.

**Но работает это только в паре с ограничением SD.** Не ограничишь `namespaces` — клиент попробует
листать поды всего кластера, и namespace-scoped Role ему этого не разрешит: получите 403 и ноль
целей. Две настройки связаны, менять их можно только вместе. Это классическая ловушка:
«я же дал права» — дал, но не на ту область.

### 3.6. Хранилище: PVC вопреки прецеденту чарта

В этом чарте postgres живёт на `emptyDir`, PVC есть только у kafka и minio. Для Prometheus всё же
берём PVC (2Gi) + `--storage.tsdb.retention.time=15d`.

Обоснование: цель диагностическая. `emptyDir` означает, что рестарт пода Prometheus стирает историю
**ровно тогда, когда её собирались смотреть** — при разборе инцидента поды и перезапускают.
2Gi на 15 дней при ~40 семействах × 3 пода — с большим запасом.

### 3.7. checksum/config — иначе правки молча не применяются

На деплоймент Prometheus вешается аннотация с хешем ConfigMap:

```yaml
annotations:
  checksum/config: {{ include (print $.Template.BasePath "/prometheus.yaml") . | sha256sum }}
```

Без неё: `helm upgrade` меняет ConfigMap, Kubernetes обновляет смонтированный файл, но **процесс
Prometheus перечитывать конфиг сам не станет**. Он продолжит работать со старым до случайного
рестарта. То есть правка keep-списка тихо не делает ничего — и это очень трудно заметить.
Смена хеша меняет pod-шаблон и заставляет деплоймент перекатить под.

Общий приём, применимый к любому приложению, читающему конфиг из ConfigMap только на старте.

### 3.8. Grafana: дашборды как код, persistence не нужна

Provisioning через три ConfigMap'а в стандартных каталогах:

- `/etc/grafana/provisioning/datasources/` — datasource на `http://prometheus:9090`
- `/etc/grafana/provisioning/dashboards/` — provider, указывающий на каталог с JSON
- `/var/lib/grafana/dashboards/` — сами дашборды

JSON лежит в репозитории как `Helm/dashboards/*.json`, втягивается через `.Files.Glob`.

Persistence Grafana **отсутствует намеренно**. Это не экономия: состояние живёт в гите, а ручная
правка в UI эфемерна by design. Хочешь изменить панель — правишь JSON и делаешь `helm upgrade`.
Иначе получается дашборд, который никто не может воспроизвести и который умирает вместе с подом.

Доступ — только `kubectl port-forward svc/grafana 3000:3000`. Через ingress не выставляем: Grafana
без TLS на публичном хосте — ровно та дыра, которую §3.1 закрывала для актуатора.

### 3.9. Новая метрика: messages_persisted_total

Счётчик в MessegerParody на месте записи в таблицу `message`, с тегом `outcome` (success/failure).

Зачем, если есть лаг консьюмера: лаг говорит «сообщения прочитаны из Kafka», но **не** «сообщения
записаны в БД». Между этими двумя событиями лежит вся логика консьюмера, и именно там терялись
сообщения в тикете `5l4`.

Прямой счётчик рядом с `kafka_consumer_fetch_manager_records_consumed_total` даёт разностную панель:

```promql
rate(kafka_consumer_fetch_manager_records_consumed_total{topic="Messages"}[5m])
  - rate(messages_persisted_total[5m])
```

Ненулевая разница = сообщения теряются между брокером и таблицей. Один график вместо часа
сопоставления логов.

**Приём в общем виде:** когда система состоит из «принял → обработал → записал», ставьте счётчик
на каждый конец и смотрите на разницу. Она обнаруживает потери, которых не видно ни на одном
из концов по отдельности.

## Часть 4. Что собираем в итоге

Отбор по хопам пути
`браузер → HTTPService → (gRPC | Kafka) → AuthService / MessegerParody → Postgres / Redis / MinIO`.

| Хоп | Метрики | Вопрос, на который отвечает |
|---|---|---|
| Живость | `up` (синтетика Prometheus), `logback_events_total{level="error"}` | Хоп мёртв целиком или просто тормозит |
| Вход HTTP | `http_server_requests_seconds_{count,sum,max,bucket}` | RED на входе: URI, статусы, p95 |
| gRPC клиент | `grpc_client_processing_duration_seconds_*`, `grpc_client_*_messages_total`, `grpc_calls_counter_total`, `grpc_call_duration_seconds_*` | Дозвонился до соседа? за сколько? |
| gRPC сервер | `grpc_server_processing_duration_seconds_*` | Клиент видит ошибку, а сервер вызова не видел = сеть/дедлайн, не логика |
| Kafka producer | `spring_kafka_template_seconds_*`, `kafka_producer_record_{send,error}_total` | Сообщение ушло в брокер? |
| Kafka consumer | `spring_kafka_listener_seconds_*` (**тег `exception`**), `..._records_lag`, `..._records_consumed_total`, `kafka_consumer_coordinator_*` | Консьюмер жив, не отстал, не падает |
| БД | `r2dbc_pool_*`, `hikaricp_connections_*` | Запись встала из-за пула? |
| Redis | `lettuce_command_completion_seconds_*` | AI-контекст |
| Бизнес | `AiRequestCounter_total`, `messages_persisted_total` | Долетело ли до таблицы `message` |
| JVM / под | `jvm_memory_used_bytes`, `jvm_gc_pause_seconds_*`, `jvm_threads_live_threads`, `process_cpu_usage`, `process_uptime_seconds`, `application_ready_time_seconds` | Под ли виноват |

**Режем:** ~195 из 204 `kafka_*` (внутренности клиента), все `*_rate` (производные от `_total`),
42 `spring_security_*`, `tomcat_sessions_*`, `jvm_buffer_*`, `jvm_classes_*`, `jvm_compilation_*`,
`disk_*`.

Ожидаемый итог: **~40 семейств на три сервиса вместо ~950** (317 × 3).

## Часть 5. Дашборды и PromQL

### 5.1. Дашборд «Путь сообщения»

Ряды строго по хопам, читается сверху вниз: где ряд краснеет — там и сломалось.

| Ряд | PromQL |
|---|---|
| 0. Живость | `up` · `sum by (app) (rate(logback_events_total{level="error"}[5m]))` |
| 1. Вход | `sum by (uri) (rate(http_server_requests_seconds_count[5m]))` · тот же с `outcome!="SUCCESS"` · `histogram_quantile(0.95, sum by (le,uri) (rate(http_server_requests_seconds_bucket[5m])))` |
| 2. gRPC | `histogram_quantile(0.95, sum by (le,method) (rate(grpc_call_duration_seconds_bucket[5m])))` · счётчики клиента против счётчиков сервера |
| 3. Kafka | send vs error по топикам · `max by (client_id,topic) (kafka_consumer_fetch_manager_records_lag)` · `sum by (exception) (rate(spring_kafka_listener_seconds_count{exception!="none"}[5m]))` |
| 4. Персистентность | `rate(kafka_consumer_fetch_manager_records_consumed_total{topic="Messages"}[5m]) - rate(messages_persisted_total[5m])` · `r2dbc_pool_pending_connections` |
| 5. Redis / AI | `rate(AiRequestCounter_total[5m])` · латентность lettuce |

### 5.2. Мини-справочник по PromQL, который тут используется

**`rate(counter[5m])`** — средний прирост счётчика в секунду за последние 5 минут.
Применяется **только к counter**. Корректно обрабатывает сброс счётчика при рестарте пода
(увидев падение значения, считает это рестартом, а не отрицательным приростом).

**`sum by (uri) (...)`** — сложить ряды, оставив разбивку только по лейблу `uri`, схлопнув остальные
(под, метод, статус). Без `by` схлопнется всё в одно число.

**`histogram_quantile(0.95, sum by (le, uri) (rate(foo_bucket[5m])))`** — читается изнутри наружу:

1. `rate(foo_bucket[5m])` — скорость наполнения каждого бакета;
2. `sum by (le, uri)` — сложить по подам, **обязательно сохранив лейбл `le`** (это граница бакета,
   без неё функция не сможет восстановить распределение) и разбивку по `uri`;
3. `histogram_quantile(0.95, ...)` — по форме распределения оценить 95-й перцентиль.

Самая частая ошибка — потерять `le` в `sum by`. Результат: `NaN` без всякой диагностики.

**`max by (client_id, topic) (kafka_..._records_lag)`** — лаг это gauge, `rate()` к нему неприменим.
Берём максимум, потому что интересует худшая партиция, а не средняя.

**Разностная панель** (`rate(A) - rate(B)`) работает только когда у A и B совпадают лейблы либо
они схлопнуты агрегацией. Иначе Prometheus не найдёт пары рядов и вернёт пустоту.

### 5.3. Дашборд «Здоровье сервисов»

Heap, паузы GC, живые треды, CPU, uptime и рестарты — разбивка по трём сервисам.
Отвечает на «под ли виноват» до того, как лезть в логику.

## Часть 6. Границы: чего метрики не умеют

**Метрики отвечают «на каком хопе просело», но не «что случилось с этим конкретным сообщением».**

Это принципиальное ограничение, а не недоработка. Метрика — агрегат: она складывает тысячу запросов
в одно число. Восстановить по ней судьбу одного запроса нельзя в принципе.

Инструмент для второго вопроса — **распределённый трейсинг** (Micrometer Tracing + Tempo/Jaeger):
сквозной trace-id, который путешествует через HTTP-заголовки, gRPC-метаданные и заголовки
Kafka-сообщений, позволяя собрать полный путь одного запроса через все сервисы.

Для сценариев вроде `5l4` («сообщения не сохраняются») трейсинг был бы точнее метрик. Он вынесен
в отдельный тикет: это самостоятельная подсистема, а не часть настройки Prometheus.

Второе ограничение было в том, что **все метрики приходили от самих приложений**, а значит
исчезали вместе с ними. Это закрыто инфра-exporter'ами — см. Часть 11.

Третьим ограничением было отсутствие записанных порогов: «что здесь считается поломкой»
каждый раз выводилось глазами по дашборду. Закрыто правилами алертинга — см. Часть 12.

## Часть 7. Как проверять, что всё работает

1. `kubectl get sa,role,rolebinding -n hybrid-platform` — RBAC на месте
2. `/api/v1/targets` у Prometheus — **6 целей** (три приложения плюс три
   инфра-exporter'а, см. Часть 11), все `up`
3. Число семейств после keep-списка ≈ 40, а не ~950
4. Снаружи `curl http://myapp.localtest.me/actuator/prometheus` → **не 200**;
   изнутри по `podIP:8090` → 200
5. Все три пода `Ready` по `/actuator/health/readiness`
6. MessegerParody: gRPC на 9091 отвечает через `grpcurl`, консьюмер читает топик
   (то есть webflux ничего не сломал)
7. Grafana: datasource `UP`, все пять дашбордов на месте, панели рисуют данные
7а. `promtool check config /etc/prometheus/prometheus.yml` в поде Prometheus —
   конфиг и файл правил валидны; `/api/v1/alertmanagers` показывает активный
   Alertmanager; `/api/v1/rules` — все правила `health: ok` (см. Часть 12)
8. Отправка сообщения → `messages_persisted_total` растёт, разностная панель = 0
9. `kubectl delete pod prometheus-…` → история пережила рестарт (проверка PVC)

**Отдельно про `promtool check config`.** Keep-регулярка собирается шаблонизатором Helm через
`join "|"`. Если она соберётся битой, Prometheus не упадёт — он молча отбросит все метрики,
и это будет выглядеть как «опять ничего не скрейпится». `promtool check config` на отрендеренном
файле ловит это до деплоя. Дешёвая проверка на очень дорогую ошибку.

## Часть 9. Грабли, собранные при реализации

Пять вещей, которых не было ни в тикете, ни в спеке — они вылезли только при
попытке всё это включить. Каждая интересна тем, что была **невидима до момента,
когда стало поздно**.

### 9.1. Micrometer разбудил спящую несовместимость

**Симптом.** После добавления `micrometer-registry-prometheus` MessegerParody перестал
стартовать:

```
APPLICATION FAILED TO START
The following method did not exist:
  'io.micrometer.core.instrument.Meter$MeterProvider
   io.micrometer.core.instrument.Counter$Builder.withRegistry(...)'
The calling method's class, net.devh.boot.grpc.client.metrics.MetricsClientInstruments
```

**Корень.** `net.devh:grpc-*-spring-boot-starter:3.1.0.RELEASE` инструментирует gRPC
через метод, появившийся в Micrometer 1.12. Spring Boot 3.1.3 приносит 1.11.3.

**Почему не проявлялось раньше.** Классы `MetricsClientInstruments` и
`MetricsServerInstruments` грузятся **только при наличии бина `MeterRegistry`**. Пока
micrometer в сервисе не было, автоконфигурация метрик не активировалась, и конфликт
лежал в classpath мёртвым грузом. Добавление метрик его разбудило.

Это общий класс проблем, стоящий запоминания: **добавление наблюдаемости активирует
код, который до того не выполнялся**. Инструментирование — не пассивная операция.

**Почему HTTPService не страдал.** У него `net.devh` версии 2.14/2.15, где этих классов
ещё не существует. То есть три сервиса одного проекта расходились по версии одной и той
же библиотеки, и никто этого не замечал, пока разница не стала значимой.

**Выбор фикса.** Было три варианта:

| Вариант | Цена |
|---|---|
| Поднять Micrometer до 1.12.x | Выход за версию, управляемую Boot 3.1.3 |
| Откатить net.devh до 2.15 | Правка транспорта между сервисами — большой радиус |
| Исключить автоконфигурации метрик net.devh | Потеря `grpc_server_processing_duration_seconds` |

Выбран первый. Третий отпадал сразу: он стоил бы ровно тех метрик хопа, ради которых
всё и затевалось (и проверка показала, что серверная часть использует тот же метод, то
есть выключение одних клиентских метрик просто сдвинуло бы падение).

Граница `1.12.x` не случайна: в 1.13 реестр Prometheus переехал с `simpleclient` на
`prometheus-metrics 1.x`, что уже несовместимо с actuator из Boot 3.1.

### 9.2. Management-порт не даёт изоляции от Spring Security

**Симптом.** `wget http://podIP:8090/actuator/health/readiness` вернул **HTML страницы
входа Google** вместо `{"status":"UP"}`.

**Корень.** `management.server.port` действительно поднимает отдельный HTTP-сервер и
**дочерний** ApplicationContext — но дочерний контекст наследует бины родительского,
включая `SecurityFilterChain`. А цепочка AuthService не имеет `securityMatcher` и
закрывает `.anyRequest().authenticated()` с `oauth2Login`. Запрос к актуатору честно
отправлялся на авторизацию в Google.

**Чем это опасно.** Prometheus получал бы редирект вместо метрик, а `readinessProbe`
никогда не увидела бы 200 и держала под вечно неготовым. Причём под при этом
запускается и работает — отказ виден только в мониторинге, которого ещё нет.

**Фикс** — отдельная цепочка с высшим приоритетом:

```java
@Bean
@Order(Ordered.HIGHEST_PRECEDENCE)
public SecurityFilterChain actuatorFilterChain(HttpSecurity http) throws Exception {
    http.securityMatcher(EndpointRequest.toAnyEndpoint())
            .authorizeHttpRequests(auth -> auth.anyRequest().permitAll())
            .csrf(AbstractHttpConfigurer::disable);
    return http.build();
}
```

`HIGHEST_PRECEDENCE` обязателен: цепочки проверяются по порядку, и без него первой
сматчилась бы catch-all.

**Важно понимать, что именно делает `permitAll` безопасным.** Не он сам по себе, а то,
что 8090 не публикуется ни в Service, ни в ingress. Безопасность здесь **сетевая, а не
прикладная** — и это осознанная модель, а не небрежность.

### 9.3. RollingUpdate плюс RWO-том — вечный ContainerCreating

Дефолтная стратегия деплоймента поднимает новый под **до** удаления старого. PVC с
`accessModes: ReadWriteOnce` не может быть примонтирован к двум подам одновременно,
поэтому новый под навсегда застревает в `ContainerCreating`, а `helm upgrade` висит.

Лечится `strategy: type: Recreate`. Правило общее: **однорепличный stateful-под на
RWO-томе обязан использовать Recreate**, и это не оптимизация, а условие работы.

### 9.4. Смена стратегии на живом Deployment: конфликт SSA с defaulting

**Симптом.** `helm upgrade` падает три раза подряд:

```
Deployment.apps "prometheus" is invalid: spec.strategy.rollingUpdate:
Forbidden: may not be specified when strategy `type` is 'Recreate'
```

При этом в чарте `rollingUpdate` не упоминается вовсе.

**Корень.** Живой Deployment был создан с `RollingUpdate`, и Kubernetes **дозаполнил**
ему `spec.strategy.rollingUpdate: {maxSurge: 25%, maxUnavailable: 25%}` — это делает
механизм defaulting, а не автор манифеста. При переходе на `Recreate` через
server-side apply Helm присылает только `type: Recreate`; дозаполненный подобъект
остаётся в живом ресурсе, потому что его никто не удалял, — и API-сервер отвергает
получившееся сочетание.

**Почему это стоит запомнить.** Ошибка указывает на поле, которого нет ни в вашем
чарте, ни в вашем git-дереве. Искать её в исходниках бесполезно: она про **состояние
живого объекта**, а не про манифест. Это общая черта server-side apply — вы описываете
желаемое, но результат сливается с тем, что уже есть, включая чужие и дозаполненные
поля.

**Фикс** — одноразовая миграция живого объекта:

```bash
kubectl -n hybrid-platform patch deploy prometheus --type merge \
  -p '{"spec":{"strategy":{"type":"Recreate","rollingUpdate":null}}}'
```

`null` в merge-патче означает «удалить ключ». Один и тот же патч и снимает лишний
подобъект, и ставит нужный тип — порознь они не сработали бы, потому что промежуточное
состояние невалидно.

Альтернатива — удалить Deployment и дать Helm создать его заново. Здесь она допустима
(Prometheus однорепличный, история на PVC), но патч аккуратнее.

**Диагностический приём в общем виде:** когда `helm upgrade` ругается на поле,
отсутствующее в чарте, сравнивайте не с манифестом, а с живым объектом:
`kubectl get <kind> <name> -o jsonpath='{.spec.<поле>}'`.

### 9.5. Проверять раньше, чем приложение стартовало

Несколько ложных тревог за сессию были одной и той же ошибкой: проверка `wget` через
15–20 секунд после `rollout restart`, тогда как Spring поднимается **32 секунды** в
MessegerParody и **46 секунд** в AuthService. Пустой ответ читался как «не работает»,
хотя означал «ещё не поднялось».

Отсюда практическое правило: сначала `kubectl logs | grep "Started Main"` или
`kubectl wait --for=condition=ready`, и только потом содержательные проверки. Ровно
эта разница между «процесс запущен» и «контекст готов» — причина, по которой
`readinessProbe` должна стоять на `/actuator/health/readiness`, а не на любом
отвечающем эндпоинте.

### 10.2. Разрешённый вопрос: синтетические метрики фильтр не проходят

В плане оставался открытым вопрос, подчиняются ли `up` и `scrape_*` правилам
`metric_relabel_configs`. Ответ получен из TSDB: там есть
`scrape_samples_post_metric_relabeling` и `scrape_series_added`, которых **нет** в
keep-списке. Значит **синтетические ряды, порождаемые самим Prometheus, фильтр метрик
не проходят** — они добавляются после него.

Практический вывод: включать `up` в keep-список не нужно, он попадёт в базу в любом
случае. Оставлен там намеренно как документация намерения — вреда не приносит, а
читающему список сразу видно, что живость целей мы собираем осознанно.

### 10.3. Одноразовый шаг при раскатке на существующий кластер

Смена стратегии деплоймента Prometheus на `Recreate` требует ручного патча живого
объекта — причина разобрана в §9.4:

```bash
kubectl -n hybrid-platform patch deploy prometheus --type merge \
  -p '{"spec":{"strategy":{"type":"Recreate","rollingUpdate":null}}}'
```

На чистом кластере шаг не нужен: там Deployment создаётся сразу с `Recreate`.

### 10.4. Что осталось непроверенным

Пункт «отправить сообщение и убедиться, что `messages_persisted_total` растёт, а
разностная панель равна нулю» требует залогиненного пользователя в браузере и
выполняется владельцем проекта. Инфраструктурная часть под него готова: метрика
зарегистрирована, ряд `messages_persisted_total` в TSDB присутствует, разностная
панель считается и возвращает данные.

## Часть 11. Инфра-exporter'ы (тикет 3nt)

### 11.1. Зачем, если метрики уже собираются

Всё, что описано в частях 1–10, приходит **от самих приложений**. У этого есть системное
свойство, которое легко не заметить: **метрика исчезает вместе с тем, кто её отдаёт.**

Три следствия, и каждое — слепая зона ровно в тот момент, когда мониторинг нужнее всего:

1. **Мёртвый консьюмер не сообщает о лаге.** `kafka_consumer_fetch_manager_records_lag` живёт
   внутри клиента Kafka в MessegerParody. Упал под — ряд пропал. На графике «консьюмер встал
   и лаг растёт» и «Prometheus перестал скрейпить» выглядят одинаково.
2. **Пул приложения не знает про общий лимит БД.** `hikaricp_connections_*` и `r2dbc_pool_*`
   показывают СВОЮ долю соединений. Упереться в `max_connections` можно втроём (плюс
   Liquibase-джоба и `psql` из отладки), и по клиентским метрикам это невидимо.
3. **Под в CrashLoopBackOff не отдаёт ничего.** Ни рестартов, ни причины падения. Панель
   «Uptime» дашборда «Здоровье сервисов» это честно признавала в своём описании.

Отсюда три экспортера, каждый смотрит со стороны инфраструктуры, а не приложения.

| Экспортер | Образ | Порт | Что видит |
|---|---|---|---|
| kafka-exporter | `danielqsj/kafka-exporter:v1.9.0` | 9308 | Офсеты и лаг групп со стороны брокера |
| postgres-exporter | `quay.io/prometheuscommunity/postgres-exporter:v0.20.1` | 9187 | Соединения, транзакции, размеры, autovacuum |
| kube-state-metrics | `registry.k8s.io/kube-state-metrics/kube-state-metrics:v2.17.0` | 8080 | Рестарты, фазы подов, реплики, PVC, джобы |

Скрейпятся тем же job'ом `kubernetes-pods` по тем же аннотациям `prometheus.io/scrape` —
отдельных scrape_config'ов не потребовалось.

### 11.2. kube-state-metrics не был в тикете

Тикет `3nt` называл двоих. Третий добавлен потому, что описание панели «Uptime» прямо
ссылалось на «kube-state-metrics, вынесенный в отдельный тикет», а такого тикета в трекере
не существовало — ссылка вела в никуда. Рестарты и `OOMKilled` не покрывались ничем.

### 11.3. RBAC: здесь ClusterRole, и это не небрежность

Prometheus намеренно получил namespace-scoped `Role` (§3.5). У kube-state-metrics —
`ClusterRole`, и обойтись Role нельзя **в принципе**: он читает `nodes`, а это
cluster-scoped ресурс, для которого namespace-scoped прав не существует.

Компенсации две. Первая — права сужены до перечисленного списка ресурсов и только
глаголов чтения. Вторая — сам экспортер запущен с `--namespaces=<namespace релиза>`,
то есть отдаёт метрики только по объектам стенда, даже имея право видеть больше.

Имя `ClusterRoleBinding` несёт префикс релиза. `ClusterRoleBinding` — объект кластерного
уровня и в namespace релиза не попадает: два релиза чарта в разных namespace'ах при
неуникальном имени затирали бы биндинг друг друга.

### 11.4. Главная ловушка: keep-список отбрасывает и экспортеры тоже

`metric_relabel_configs` с `action: keep` действует на **все** цели job'а `kubernetes-pods`.
Поднять экспортер и не добавить его метрики в `prometheus.keepMetrics` — значит получить
цель в состоянии `up`, ноль сохранённых рядов и панели с «No data». Отличить это от
«экспортер сломан» по дашборду невозможно.

Поэтому имена метрик в keep-список **сняты с живого скрейпа каждого экспортера**, а не
взяты по памяти. Проверка была не формальной — ожидаемые имена разошлись с реальными:

- `pg_stat_bgwriter_*` оканчиваются на `_total` (`pg_stat_bgwriter_checkpoints_timed_total`);
- размер базы живёт отдельным семейством `pg_database_size_bytes`, а не внутри
  `pg_stat_database_*`;
- у kafka-exporter есть и `kafka_consumergroup_lag`, и `kafka_consumergroup_lag_sum` —
  разной размерности, и на дашборде они не взаимозаменяемы.

Напоминание из §3.4 действует и здесь: Prometheus якорит регулярку целиком, поэтому
каждый элемент обязан описывать имя метрики полностью.

### 11.5. Отдельно про pg_settings_*

postgres-exporter отдаёт **около 250 семейств** `pg_settings_*` — это статическая
конфигурация БД (`autovacuum_naptime_seconds`, `enable_hashjoin`, `jit_above_cost` и так
далее). Она не меняется до рестарта постгреса, и держать её в TSDB бессмысленно: ровно тот
же «собираем на все случаи жизни», против которого воевала §2.2.

В keep-списке оставлен ровно один — `pg_settings_max_connections`. Он нужен как
**знаменатель**: без него `pg_stat_activity_count = 31` не поддаётся истолкованию.

### 11.6. Новые дашборды

| Дашборд | uid | Отвечает на |
|---|---|---|
| Kafka со стороны брокера | `kafka-broker` | Лаг групп, темп записи против темпа разбора, живы ли участники группы |
| PostgreSQL | `postgres` | Соединения от лимита, долгие транзакции, commit/rollback, кэш, мёртвые кортежи, размеры |
| Нагрузки Kubernetes | `kubernetes-workloads` | Рестарты, причина последнего падения, застрявшие контейнеры, реплики, PVC, джобы |

Пара панелей на дашборде Kafka строится в расчёте на конкретный сценарий: «темп записи в
топики» рядом с «темпом разбора консьюмерами» — это картина тикета `5l4`, где сообщения
уходили в топик `Messages`, а читателя у него не было. Расхождение линий видно мгновенно.

### 11.7. Грабли: --reuse-values не подхватывает новые ключи чарта

`helm upgrade --reuse-values` берёт за основу **вычисленные значения прошлого релиза**, а не
дефолты новой версии чарта. Новые ключи (`infra.kafkaExporter` и соседние) в этой базе
отсутствуют, поэтому шаблоны с `{{- if }}` по ним не отрендерились вовсе.

Провал тихий: `helm upgrade` отчитывается «Upgrade complete», ревизия растёт, а подов нет.
Рабочий флаг — `--reset-then-reuse-values`: он берёт дефолты нового чарта и заново
накладывает поверх пользовательские `--set` (включая секреты).

### 11.8. Грабли: kind load спотыкается на multi-arch манифестах

`kind load docker-image` на всех трёх образах падал с `ctr: content digest … not found` —
образы мультиархитектурные, и локальный слой нужного digest'а не содержит. Обходить не
пришлось: узел kind тянет их из интернета сам. Загрузка через `kind load` обязательна только
для образов, собранных локально и нигде не опубликованных, — то есть для трёх наших сервисов.

### 11.9. Проверено живьём

- `/api/v1/targets`: 6 целей, все `up` (3 приложения + 3 экспортера).
- Ряды в TSDB: `kafka_consumergroup_lag` — 20, `kafka_topic_partitions` — 13,
  `pg_stat_activity_count` — 26, `pg_stat_user_tables_n_live_tup` — 6,
  `kube_pod_container_status_restarts_total` — 12, `kube_deployment_status_replicas_available` — 12.
- Шум отфильтрован: `pg_settings_autovacuum` и `go_goroutines` в TSDB отсутствуют.
- Grafana: все пять дашбордов зарегистрированы, запросы панелей возвращают данные с
  ожидаемыми лейблами (`datname`, `relname`, `state`, `mode`, `consumergroup`, `topic`,
  `pod`, `container`, `persistentvolumeclaim`).

Непроверенным осталось одно: семейства `kube_job_*`. Джобы чарта (liquibase, kafka-topics,
minio-provision) висят на Helm-хуках и удаляются после успеха, поэтому в момент проверки
объектов Job в кластере не было и снять имена со скрейпа было не с чего. Имена взяты из
схемы kube-state-metrics и проверятся первым же прогоном хуков на чистой установке.

## Часть 12. Алертинг: правила и Alertmanager (тикет zei)

### 12.1. Тикет был прав, но не в том, в чём казалось

`zei` заводился как YAGNI: «стенд с одним пользователем, который смотрит дашборд по
запросу — алерты некому доставлять». Это верно **про доставку** и остаётся верным:
ни одного настоящего приёмника здесь нет и не заводилось.

Но ценность тикета оказалась в другой половине. **Правило алертинга — это записанный
ответ на вопрос «что в этой системе считается поломкой».** Без него ответ каждый раз
выводится заново, глазами, по дашборду, и зависит от того, кто смотрит и насколько
он выспался. Шестнадцать правил в `Helm/templates/prometheus-rules.yaml` — это
формализованные пороги, а не механизм уведомлений.

Поэтому разделение получилось такое:

- **Правила живут в Prometheus** и работают независимо от `infra.alertmanager`.
  Выключите тумблер — срабатывания всё равно видны в Prometheus `/alerts`.
- **Alertmanager** добавляет группировку, дедупликацию и гашение: превращает поток
  «условие истинно каждые 15 секунд» в список активных проблем.

### 12.2. Что покрыто правилами

| Группа | Правила |
|---|---|
| `liveness` | TargetDown, PodCrashLooping, ContainerOOMKilled, DeploymentReplicasUnavailable, PersistentVolumeClaimPending |
| `http` | HttpServerErrorRate, TokenExchangeFailing |
| `kafka` | KafkaConsumerGroupEmpty, KafkaConsumerLagGrowing, KafkaProducerErrors |
| `postgres` | PostgresDown, PostgresConnectionsHigh, PostgresLongRunningTransaction, PostgresDeadlocks |
| `business` | MessagesConsumedButNotPersisted, ApplicationErrorLogs |

Три правила стоит выделить, потому что они прицельные, а не типовые:

- **`KafkaConsumerGroupEmpty`** невозможно построить на клиентских метриках в принципе:
  мёртвый консьюмер их не отдаёт. Правило существует только благодаря kafka-exporter
  (Часть 11) и покрывает ровно состояние тикета `5l4`.
- **`MessagesConsumedButNotPersisted`** — разностное: консьюмер разбирает топик
  `Messages`, а `messages_persisted_total` не растёт в том же темпе. По отдельности ни
  одна из двух метрик этот разрыв не показывает.
- **`TokenExchangeFailing`** — отдельно от общего `HttpServerErrorRate`, потому что общий
  порог этот случай размывает: на фоне остального трафика доля 5xx остаётся ниже 5%, а
  вход при этом сломан у всех. Известная причина — квота Gemini на пути refresh (`kz6`).

`PodCrashLooping` считает `increase(...[15m]) > 3`, а не мгновенное значение счётчика:
счётчик рестартов растёт и после единичного давнего падения, и алерт по нему висел бы
вечно. Порог 3 отделяет CrashLoopBackOff от одного рестарта при выкатке.

### 12.3. Правило на отфильтрованную метрику не сработает никогда

Тот же класс тихой поломки, что и в §11.4, только на этаж выше: выражение правила
опирается на метрики, **уже прошедшие** `keep`-список. Если метрику отфильтровали,
правило останется `inactive` навсегда — без ошибки, без предупреждения, с `health: ok`.

Поэтому проверка не ограничивалась `promtool`: для каждой метрики из каждого правила
отдельно проверено, что ряд в TSDB существует. Это выявило одну (см. §12.6).

### 12.4. Проверка доставки: канареечное правило

`health: ok` и `state: inactive` у всех правил **не доказывают**, что алерт дойдёт до
Alertmanager, — они доказывают лишь, что выражение синтаксически верно и сейчас ложно.
Между «правило сработало» и «алерт виден» лежит доставка, которую ничто из этого не
проверяет.

Проверено канарейкой: во временно добавленное правило `expr: vector(1)` (всегда истинно),
затем прослежен весь путь — Prometheus `/api/v1/alerts` показал `firing`, Alertmanager
`/api/v2/alerts` показал тот же алерт со `state: active` и `receivers: [blackhole]`.
После проверки правило удалено.

### 12.5. Грабли

**(а) Prometheus падает на битом файле правил — и это хорошо.** Ошибка отступа в
`alerts.yml` уводит под в CrashLoopBackOff с внятным сообщением
(`field name not found in type rulefmt.Rule`, с номером строки). В отличие от битой
keep-регулярки, которая отбрасывает всё молча, здесь поломка громкая.

**(б) `kubectl apply` на объект, которым владеет Helm, ломает следующий `helm upgrade`.**
Ручная правка ConfigMap через `kubectl create ... | kubectl apply -f -` назначает
менеджером поля `kubectl-client-side-apply`, и последующий `helm upgrade` падает с
`conflict occurred while applying object ... conflict with "kubectl-client-side-apply"`.

Опасность в том, как это выглядит: команда завершается, вывод длинный, и без явной
проверки легко решить, что откат произошёл. Лечится удалением объекта — Helm пересоздаст
его на следующем upgrade. Родственно §9.4, где тот же механизм SSA конфликтовал с
defaulting'ом на живом Deployment.

**(в) `include` файла из него самого = "nested reference".** Deployment Alertmanager
считает checksum от своего ConfigMap; в одном файле шаблон включал бы сам себя. Helm
выдаёт стену повторяющегося текста, из которой причина не читается. Поэтому конфиг
вынесен в `alertmanager-config.yaml` — ровно то же разделение, что у Prometheus.

### 12.6. Найдено при проверке: продюсер Kafka не отдаёт метрик

Из восемнадцати метрик, используемых правилами, семнадцать присутствуют в TSDB.
Отсутствует одна — `kafka_producer_record_error_total` (правило `KafkaProducerErrors`).

Проверено, что дело **не в keep-фильтре**: в сыром скрейпе `httpservice:8090` нет
ни одного семейства `kafka_producer_*` — ноль. При этом `kafka_consumer_*` там же есть.

Причина в том, что `KafkaTemplate` создаёт экземпляр продюсера **лениво, при первой
отправке**, тогда как слушатели консьюмера стартуют вместе с контекстом. Пока сервис не
отправил ни одного сообщения после рестарта, продюсера не существует и привязывать
метрики не к чему. Собственного `ProducerFactory` в HTTPService нет
(`KafkaProducer.java` инжектит автоконфигурируемый `KafkaTemplate`), так что
автоконфигурация метрик не отключена — она просто не к чему применяться.

Практический вывод: правило `KafkaProducerErrors` не сломано, но становится живым
только после первой отправки сообщения. Запись `kafka_producer_record_(send|error)_total`
в keep-списке пришла ещё из `c2k` и была так же неактивна — это не регрессия алертинга.

### 12.7. Как сделать доставку настоящей

Заменить приёмник `blackhole` в `templates/alertmanager-config.yaml` на реальный
(`webhook_configs`, `email_configs`, telegram) и указать его в `route.receiver`.
Больше ничего менять не требуется: правила, маршрутизация, группировка и гашение уже
настроены. `inhibit_rules` гасит `warning` по сервису, пока по нему висит `critical`,
чтобы упавшая цель не порождала лавину следствий.
