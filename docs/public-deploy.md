# Публикация стенда наружу по HTTPS

Как приложение отдаётся в интернет на настоящем домене. Описывает текущее устройство и
порядок раскатки; локальный стенд (`http://myapp.localtest.me`) при этом не меняется —
все значения ниже переключаются явно и по умолчанию выключены.

## Схема

```
браузер --https:443--> Caddy (хост VM) --http:8081--> ingress-nginx (127.0.0.1) --> сервисы
```

TLS терминируется **до** кластера. Внутрь трафик идёт по обычному HTTP, поэтому
`tls.enabled` в чарте остаётся `false`: tls-секция в Ingress включила бы у ingress-nginx
`ssl-redirect` сразу на всех путях, включая `auth_request` к `/jwtcheck` и
SockJS-хендшейк, которым редиректить некуда.

Кластер слушает **только loopback**. Единственный процесс, доступный снаружи, — Caddy;
обойти его и постучаться в ingress напрямую неоткуда, и это свойство конфигурации, а не
firewall-правил.

## Почему нужен домен, а не IP

Google не принимает IP-адрес в качестве хоста в OAuth redirect URI — исключение сделано
только для `localhost`. То есть сертификат на голый IP дал бы HTTPS, но вход через Google
всё равно бы не заработал. Отсюда бесплатный домен (DuckDNS) вместо
IP-сертификата.

## Что нужно подготовить руками

1. **Домен указывает на VM.** `dig +short gyattalert.duckdns.org` обязан вернуть внешний IP машины.
   У GCP-инстанса внешний IP по умолчанию *ephemeral* и меняется при пересоздании —
   либо резервируй static, либо обновляй запись DuckDNS по крону.
2. **Firewall облака: открыты 80 и 443.** Порт 80 нужен не «на всякий случай», а для
   HTTP-01: Let's Encrypt ходит на `http://gyattalert.duckdns.org/.well-known/acme-challenge/`.
3. **Google OAuth-клиент** (<https://console.cloud.google.com/apis/credentials>) →
   Authorized redirect URIs → добавить `https://gyattalert.duckdns.org/login/oauth2/code/google`.
   Сверка строго точная, включая схему. Старый localtest.me-адрес можно оставить рядом.

   Приложение при этом останется в режиме **Testing**: поле Authorized domains на consent
   screen требует подтверждения владения доменом через Search Console, а `duckdns.org`
   принадлежит не нам. Вход через Google работает для аккаунтов из списка тестовых
   пользователей; обычный вход по паролю этим не ограничен.

## Инструменты

Из внешнего на сервере обязателен только **Docker** — его скрипт не ставит: это демон,
репозиторий пакетов и членство в группе с перелогином, то есть изменение состояния машины
сильнее, чем ждут от скрипта раскатки.

`kind`, `kubectl` и `helm` `deploy-kind.sh` доустанавливает сам, если не находит их в
PATH: качает с официальных адресов проектов, сверяет контрольные суммы там, где они
публикуются, и кладёт в `/usr/local/bin`. Версии прибиты в самом скрипте и совпадают с
теми, на которых проект гоняется локально — раскатка, тянущая «последний релиз» в момент
запуска, воспроизводима только до следующего мажора у любого из трёх проектов.

**Caddy** ставится тоже, но только в публичном режиме (`PUBLIC=true` или `PUBLIC_HOST`) —
на локальном стенде прокси перед кластером нет вовсе, и требовать его на машине
разработчика незачем. Ставится он через официальный apt-репозиторий проекта, а не готовым
бинарником как остальные три: пакет приносит systemd-юнит и системного пользователя, а
прокси на сервере обязан переживать перезагрузку.

**Настраивать Caddy скрипт не будет.** `/etc/caddy/Caddyfile` — конфигурация машины, а не
этого проекта: тот же прокси может обслуживать и другие сайты, и переписать его файл из
раскатки значило бы уронить чужой сервис. Образец для чистой машины, где Hybrid
единственный, — `deploy/Caddyfile` в репозитории.

Переопределяется переменными: `KIND_VERSION`, `KUBECTL_VERSION`, `HELM_VERSION`,
`TOOLS_BIN_DIR`. `AUTO_INSTALL_TOOLS=false` выключает докачку — тогда скрипт просто
падает со списком недостающего и ссылками.

Автоустановка работает только на Linux. На машине разработчика инструменты ставятся
пакетным менеджером и уже есть.

## Раскатка

Если на сервере данные вынесены на отдельный диск, сначала прочитай
[docs/vm-data-disk.md](vm-data-disk.md): раскатка тянет за собой образы, кэш сборки и всю
файловую систему ноды кластера, и по умолчанию всё это уезжает туда, куда настроен Docker.

```bash
# 1. Пересоздать кластер: проброс портов задаётся ТОЛЬКО при создании,
#    у живого кластера его не поменять (скрипт это проверяет и останавливается).
kind delete cluster --name hybrid

# 2. Одна переменная. PUBLIC=true сам уводит ingress на 127.0.0.1:8081/8443,
#    включает доверие к X-Forwarded-* и подмешивает values-public.yaml с доменом.
PUBLIC=true ./deploy-kind.sh

# 3. Прокси на хосте
PUBLIC_HOST=gyattalert.duckdns.org caddy run --config deploy/Caddyfile
```

Домен проекта — `gyattalert.duckdns.org` — зашит в `Helm/values-public.yaml`, поэтому
называть его в команде не нужно. Раскатать на другом домене:
`PUBLIC_HOST=<другой> ./deploy-kind.sh` — эта переменная перекрывает домен из overlay и
сама по себе включает публичный режим.

Посмотреть, что именно уедет в кластер, до применения:

```bash
helm template hybrid ./Helm -f Helm/values-public.yaml | grep -E 'host:|INGRESS_HOST|PUBLIC_SCHEME|COOKIE_SECURE'
```

Overlay подмешивает **скрипт**, а не отдельная команда `helm upgrade` следом, и это не
вопрос удобства. Ключи подписи минтятся во временный каталог, который удаляется по
`trap EXIT`; повторный `helm upgrade` без `--set-file` откатил бы приватный ключ к
плейсхолдеру из `values.yaml` — то есть починил бы домен и сломал выдачу токенов.

## Что именно переключается и почему вместе

| Значение | http-стенд | публикация | Что ломается, если не переключить |
|---|---|---|---|
| `global.publicScheme` | `http` | `https` | redirect-uri собирается по http → Google отдаёт `redirect_uri_mismatch` |
| `global.cookieSecure` | `false` | `true` | refresh-кука уходит без `Secure` и отдаётся по обычному HTTP |
| `global.forwardHeadersStrategy` | `none` | `framework` | Spring считает соединение http'шным и строит http-адреса |
| `global.extraAllowedOrigins` | `http://localhost` | `""` | лишний разрешённый Origin на публичном хосте |
| `INGRESS_USE_FORWARDED_HEADERS` | `false` | `true` | см. ниже — самая неочевидная из связок |
| `KIND_HTTP_HOST_PORT` / `KIND_HTTPS_HOST_PORT` | `80` / `443` | `8081` / `8443` | kind дерётся с Caddy за порты и не стартует |
| `KIND_LISTEN_ADDRESS` | `0.0.0.0` | `127.0.0.1` | ingress доступен снаружи в обход прокси |

Все значения в колонке «публикация» — **дефолты режима**, их задаёт `PUBLIC=true`.
Переопределять по одному можно, но обычно не нужно; смысл в том, что забыть одну из
переменных больше нельзя. Отдельно про пару портов: при переносе только HTTP-порта kind
падает на `failed to bind host port 127.0.0.1:443: address already in use` — HTTPS-маппинг
остаётся на 443, который держит Caddy. Кластеру 443 не нужен и по существу: TLS
терминирует прокси, внутрь трафик идёт по обычному HTTP.

Ловушка с последней строкой стоит отдельного абзаца. `forwardHeadersStrategy: framework`
сам по себе бесполезен, если ingress-nginx не пробрасывает заголовки: в его
`lua_ingress.lua` схема перезаписывается из `X-Forwarded-Proto` **только** под
`if config.use_forwarded_headers`, а иначе остаётся равной `$scheme` — то есть `http`,
потому что участок Caddy → ingress именно такой. Результат: Spring уверенно считает
соединение незащищённым на полностью рабочем HTTPS, и симптом выглядит как ошибка
приложения, а не прокси.

Обратная сторона — доверять `X-Forwarded-*` значит позволить клиенту объявить схему
своего соединения самому. Поэтому флаг включается только вместе с
`KIND_LISTEN_ADDRESS=127.0.0.1`: тогда единственный, кто способен прислать эти заголовки,
— локальный Caddy.

### Схемы мало — нужен ещё порт

Второй заголовок той же связки, и без него всё выглядит рабочим до последнего шага входа.
Caddy проставляет `X-Forwarded-For`, `-Proto` и `-Host`, но **не** `-Port`. Ingress-nginx
тогда подставляет свой собственный порт — 80, потому что участок Caddy → ingress идёт по
plain HTTP.

Дальше вступает то, что приложение делает **относительные** редиректы:
`sendRedirect("/authcallback?...")` в `AuthSuccessHandler`. Абсолютный адрес из него
собирает сервлет-контейнер, беря схему, хост и порт из заголовков. Получается
`https://<домен>:80/authcallback` — браузер жмёт TLS в порт, где его нет, и вход падает
уже ПОСЛЕ успешного возврата от Google. Симптом обманчивый: Google-авторизация прошла,
`state` и `code` в адресе есть, а страница не открывается.

Лечится строкой в `reverse_proxy` (см. `deploy/Caddyfile`):

```
header_up X-Forwarded-Port 443
```

Константа, а не переменная: снаружи публичный порт всегда 443 — на другом HTTPS-порту не
работает ни HTTP-01, ни TLS-ALPN-01, то есть сертификата не было бы вовсе.

## Известное ограничение раскатки

`deploy-kind.sh` заново минтит ключи подписи при каждом запуске, и два ключа ведут себя
по-разному:

- `REFRESH_SECRET` берётся из `.env`, если он там есть, и генерируется случайным только
  как fallback. Для живущего стенда его надо зафиксировать в `.env` — иначе каждый прогон
  скрипта обесценивает все выданные refresh-токены, то есть разлогинивает всех, кому уже
  дали ссылку.
- RSA-пара для JWT генерируется **безусловно** (`openssl genpkey` перед `helm deploy`) и
  переменной окружения не переопределяется. Переживают это только уже выпущенные
  access-токены — они короткоживущие, и клиент молча берёт новый по refresh-куке. Но если
  понадобится переживать редеплой полностью, ключ придётся выносить из скрипта в секрет.
