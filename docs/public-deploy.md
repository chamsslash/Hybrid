# Публикация стенда наружу по HTTPS

Как приложение отдаётся в интернет на настоящем домене. Описывает текущее устройство и
порядок раскатки; локальный стенд (`http://myapp.localtest.me`) при этом не меняется —
все значения ниже переключаются явно и по умолчанию выключены.

## Схема

```
браузер --https:443--> Caddy (хост VM) --http:8081--> ingress-nginx (127.0.0.1) --> сервисы
```

TLS терминируется **до** кластера. Внутрь трафик идёт по обычному HTTP, поэтому
`tls.enabled` в чарте остаётся `false`: tls-секция в Ingress включила бы у ingress-nginx
`ssl-redirect` сразу на всех путях, включая `auth_request` к `/jwtcheck` и
SockJS-хендшейк, которым редиректить некуда.

Кластер слушает **только loopback**. Единственный процесс, доступный снаружи, — Caddy;
обойти его и постучаться в ingress напрямую неоткуда, и это свойство конфигурации, а не
firewall-правил.

## Почему нужен домен, а не IP

Google не принимает IP-адрес в качестве хоста в OAuth redirect URI — исключение сделано
только для `localhost`. То есть сертификат на голый IP дал бы HTTPS, но вход через Google
всё равно бы не заработал. Отсюда бесплатный домен (DuckDNS) вместо
IP-сертификата.

## Что нужно подготовить руками

1. **Домен указывает на VM.** `dig +short <домен>` обязан вернуть внешний IP машины.
   У GCP-инстанса внешний IP по умолчанию *ephemeral* и меняется при пересоздании —
   либо резервируй static, либо обновляй запись DuckDNS по крону.
2. **Firewall облака: открыты 80 и 443.** Порт 80 нужен не «на всякий случай», а для
   HTTP-01: Let's Encrypt ходит на `http://<домен>/.well-known/acme-challenge/`.
3. **Google OAuth-клиент** (<https://console.cloud.google.com/apis/credentials>) →
   Authorized redirect URIs → добавить `https://<домен>/login/oauth2/code/google`.
   Сверка строго точная, включая схему. Старый localtest.me-адрес можно оставить рядом.

   Приложение при этом останется в режиме **Testing**: поле Authorized domains на consent
   screen требует подтверждения владения доменом через Search Console, а `duckdns.org`
   принадлежит не нам. Вход через Google работает для аккаунтов из списка тестовых
   пользователей; обычный вход по паролю этим не ограничен.

## Раскатка

```bash
# 1. Кластер: ingress уезжает на loopback:8081 и начинает доверять X-Forwarded-* от Caddy
KIND_HTTP_HOST_PORT=8081 \
KIND_LISTEN_ADDRESS=127.0.0.1 \
INGRESS_USE_FORWARDED_HEADERS=true \
./deploy-kind.sh

# 2. Чарт: публичный overlay + домен
helm upgrade --install hybrid ./Helm -n hybrid-platform \
  -f Helm/values.yaml -f Helm/values-public.yaml \
  --set global.ingressHost=<домен> \
  --set ingress.host=<домен> \
  ...секреты как обычно...

# 3. Прокси на хосте
PUBLIC_HOST=<домен> caddy run --config deploy/Caddyfile
```

## Что именно переключается и почему вместе

| Значение | http-стенд | публикация | Что ломается, если не переключить |
|---|---|---|---|
| `global.publicScheme` | `http` | `https` | redirect-uri собирается по http → Google отдаёт `redirect_uri_mismatch` |
| `global.cookieSecure` | `false` | `true` | refresh-кука уходит без `Secure` и отдаётся по обычному HTTP |
| `global.forwardHeadersStrategy` | `none` | `framework` | Spring считает соединение http'шным и строит http-адреса |
| `global.extraAllowedOrigins` | `http://localhost` | `""` | лишний разрешённый Origin на публичном хосте |
| `INGRESS_USE_FORWARDED_HEADERS` | `false` | `true` | см. ниже — самая неочевидная из связок |

Ловушка с последней строкой стоит отдельного абзаца. `forwardHeadersStrategy: framework`
сам по себе бесполезен, если ingress-nginx не пробрасывает заголовки: в его
`lua_ingress.lua` схема перезаписывается из `X-Forwarded-Proto` **только** под
`if config.use_forwarded_headers`, а иначе остаётся равной `$scheme` — то есть `http`,
потому что участок Caddy → ingress именно такой. Результат: Spring уверенно считает
соединение незащищённым на полностью рабочем HTTPS, и симптом выглядит как ошибка
приложения, а не прокси.

Обратная сторона — доверять `X-Forwarded-*` значит позволить клиенту объявить схему
своего соединения самому. Поэтому флаг включается только вместе с
`KIND_LISTEN_ADDRESS=127.0.0.1`: тогда единственный, кто способен прислать эти заголовки,
— локальный Caddy.

## Известное ограничение раскатки

`deploy-kind.sh` заново минтит ключи подписи при каждом запуске, и два ключа ведут себя
по-разному:

- `REFRESH_SECRET` берётся из `.env`, если он там есть, и генерируется случайным только
  как fallback. Для живущего стенда его надо зафиксировать в `.env` — иначе каждый прогон
  скрипта обесценивает все выданные refresh-токены, то есть разлогинивает всех, кому уже
  дали ссылку.
- RSA-пара для JWT генерируется **безусловно** (`openssl genpkey` перед `helm deploy`) и
  переменной окружения не переопределяется. Переживают это только уже выпущенные
  access-токены — они короткоживущие, и клиент молча берёт новый по refresh-куке. Но если
  понадобится переживать редеплой полностью, ключ придётся выносить из скрипта в секрет.
