# Live-verification runbook: SPA-миграция (Вариант 2) + auth-контракт (820/x7m)

Дата: 2026-07-26
Цель: живьём в kind проверить (1) SPA-навигацию без перезагрузок и строгую CSP/Trusted-Types,
(2) регрессию контракта `sub` (820) и сообщение неверного пароля (x7m). Один деплой — обе проверки.

## Шаг 0. Подготовка деплой-состояния

SPA-ветка `feat/spa-migration-v2` **не содержит** auth-фиксы из `dev` (ветвилась раньше их мёржа).
Чтобы гонять SPA+820 вместе, слить `dev` в SPA-ветку (в SPA-worktree), затем деплоить её:
```
cd <spa-base-worktree>
git merge dev            # принести auth-фиксы (820/x7m/squ/iy0) в SPA-ветку
mvn -q test (оба модуля, JDK21)   # убедиться, что объединение зелёное
```
Ожидаемый конфликт: `welcome.js` (auth-фикс редактировал / SPA удаляет) → резолв **в пользу
удаления** (iy0-фикс уже во `welcome.view.js`). `callback.js` — берём версию с auth-фиксом.

## Шаг 1. Деплой в kind

`/kdeploy` (прогон `deploy-kind.sh` из SPA-worktree) → дождаться, что все поды Ready:
AuthService, HTTPService (MessegerParody), Redis, Kafka, MinIO, Postgres, ingress.
Если под падает — `/kdebug <pod>` (describe+events+logs).

Доступ к приложению: определить URL (ingress host / port-forward на HTTPService:8080).
Зафиксировать базовый URL для браузера.

## Шаг 2. Ограничения / предпосылки

- **Google-OAuth**: нужен реальный Google client (beads `gq9`, открыт). Если креды не настроены —
  Google-путь live НЕ проверяем; помечаем как «не покрыто» (это НЕ регрессия). Проверяем только,
  что кнопка Google уводит на `accounts.google.com` (сам redirect).
- **Silent-refresh тест (820)**: истечение access ~15 мин (`jwt-expiration-ms=900000`). Чтобы не
  ждать — форсировать: либо в DevTools очистить in-memory токен и дёрнуть защищённый `/api/*`
  (получим 401 → интерцептор вызовет `/exchangeTokens`), либо вручную `POST /exchangeTokens` с
  refresh-cookie. Проверяем ответ: **200** (а не 403) и продолжение сессии.

## Шаг 3. Прогон A — auth-контракт (820 + x7m)

Через браузер (Chrome MCP), фиксировать Network + консоль:

- **A1. Регистрация не-Google юзера.** Открыть `/welcome` → «регистрация» → заполнить форму →
  сабмит. Ожидание: попадаем в chatlist залогиненными (register всегда ставил sub — база-кейс).
- **A2. Обычный логин.** Выйти/новая сессия → `/welcome` → ввести логин/пароль → сабмит.
  Ожидание: 200, редирект в chatlist. В Network у `/reactive/login` — тело с accessToken.
- **A3. 🎯 820 silent-refresh (главный).** В залогиненной сессии не-Google юзера форсировать
  refresh (см. Шаг 2). Ожидание: `POST /exchangeTokens` → **200**, новый accessToken, сессия
  жива, **нет редиректа на /welcome**. (До фикса тут был 403 → разлогин.)
- **A4. x7m неверный пароль.** `/welcome` → верный логин + НЕВЕРНЫЙ пароль → сабмит.
  Ожидание: понятное сообщение «Invalid username or password» (или его текст), **не** generic
  «Отсутствуют данные формы» / «Request failed with status code…».
- **A5. Консистентность sub (косвенно).** После A2 в залогиненной сессии `/api/me` и
  `/api/chatlist` возвращают данные (не пустой userId) → значит sub-principal корректен.

## Шаг 4. Прогон B — SPA-миграция (Вариант 2)

Фиксировать: в Network **отсутствие document-перезагрузок** там, где их не должно быть; в консоли
**нет CSP-violation, нет Trusted-Types-ошибок, нет двойного createPolicy('default')**.

- **B1.** `/welcome` — shell грузится один раз, форма логина видна, стили на месте (style_welcome).
- **B2.** Ссылка «регистрация» → URL меняется на `/registerpage`, **без reload**, форма регистрации.
- **B3. 🎯 q1b.** Успешная регистрация → URL `/reactive/chatlist`, **без reload**, повторный логин
  НЕ требуется, **нет запроса `/exchangeTokens`** (токен пережил навигацию).
- **B4.** Клик по чату → `/reactive/chat?id=…`, документ не перезагружается, сообщения грузятся,
  STOMP подключён (WS-соединения в Network).
- **B5. 🎯 STOMP teardown.** Кнопка «назад» браузера → chatlist без reload. Проверить, что число
  открытых SockJS/WS-соединений **не растёт** (старый STOMP чата отключён, нет дублей подписок).
- **B6.** Создать чат → `/reactive/createchat` → сабмит → возврат в chatlist **без reload**, новый
  чат виден (бэкенд отдаёт 200 JSON, клиент навигирует).
- **B7.** F5 на `/reactive/chat?id=…` → сервер отдаёт shell, JS рисует чат, сессия восстановлена
  silent-refresh'ом.
- **B8.** Кнопка Google на `/welcome` → уход на `accounts.google.com` (реальная навигация — ок).
- **B9. Консоль (строгая политика).** На протяжении всего прохода: нет `Refused to … Content
  Security Policy`, нет `TrustedHTML`/Trusted-Types-ошибок, нет `Failed to execute 'createPolicy'`.

## Шаг 5. Прогон C — взаимодействие (820 + SPA вместе)

- **C1.** Логин паролем (A2) → пройтись по SPA (B4→B5→B6) → F5 (B7) → сессия выживает и данные
  грузятся. Подтверждает, что numeric-sub и SPA-навигация работают совместно.

## Критерии приёмки прогона

Всё из A1–A5 (кроме Google, если нет кред), B1–B9, C1 — зелёное; консоль чистая по CSP/TT.
При провале любого 🎯-пункта — фиксируем root cause, заводим/обновляем beads, чиним до мёржа
SPA в `dev`. При зелёном — закрываем 820 (live-regression выполнена) и мёржим SPA в `dev`.
