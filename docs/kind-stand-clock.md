# Часы VM и задержка сообщений на стенде

Документ описывает один конкретный класс отказа: **часы Linux-VM, внутри которой живёт
kind-кластер, расходятся с часами хоста**. Симптом со стороны приложения — сообщения
чата доезжают до Postgres с задержкой в десятки секунд, что выглядит неотличимо от
потери сообщений. Диагностика этого симптома с нуля стоит дорого, поэтому она записана
здесь целиком (beads 75d).

## Симптом

Со стороны браузера: сообщение отправляется, отрисовывается мгновенно (это STOMP-эхо,
оно не ходит через Kafka), но в таблице `message` не появляется. Через 40–50 секунд
запись всё-таки возникает.

Со стороны консьюмера (`MessegerParody`) — цикл в логах, до нескольких событий в секунду
на каждом члене группы:

```
Discovered group coordinator kafka:9092
Group coordinator is unavailable or invalid due to cause: coordinator unavailable
Requesting disconnect
```

Со стороны брокера:

```
[NodeToControllerChannelManager id=1 name=heartbeat] Disconnecting from node 1 due to request timeout.
Cancelled in-flight BROKER_HEARTBEAT request ... (elapsed time since creation: 4504ms, request timeout: 4500ms)
[BrokerLifecycleManager id=1] Unable to send a heartbeat because the RPC got timed out before it could be sent.
```

Брокер не успевает достучаться до **собственного** KRaft-контроллера на `localhost:9093`
(одна JVM, `KAFKA_PROCESS_ROLES=broker,controller`). Таймаут 4500 мс — это половина
`broker.session.timeout.ms` (9000 мс).

## Root cause

`CLOCK_REALTIME` внутри VM периодически прыгает вперёд и тут же возвращается назад,
при этом монотонные часы идут ровно. Замер на стенде — 900 сэмплов с шагом 200 мс за
181 секунду монотонного времени:

```
forward jumps: 16 (avg +39.36 s), backward: 16
```

То есть примерно раз в 10 секунд `date` на ~200 мс начинает показывать время на 39 секунд
вперёд, после чего возвращается к прежнему значению. Базовое смещение часов VM
относительно хоста при этом стабильно: −39.2 с.

Kafka считает таймауты запросов по **wall-clock** (`Time.SYSTEM.milliseconds()`, то есть
`System.currentTimeMillis()`), а не по монотонным часам. Поэтому скачок wall-clock
напрямую ломает учёт времени жизни in-flight запроса:

- запрос, созданный в момент «высокого» отсчёта, получает `createdMs` на 39 с в будущем;
  его расчётное время жизни становится отрицательным и остаётся таковым ~39 секунд
  реального времени — heartbeat висит в полёте вместо положенных 4.5 с;
- всё это время брокер не подтверждает свою живость контроллеру и не годится клиентам
  как координатор группы — отсюда цикл `coordinator unavailable` у консьюмеров;
- консьюмер не забирает сообщение из топика `Messages`, пока группа не стабилизируется,
  и запись в `message` появляется с задержкой того же порядка (~40–50 с).

Брокер при этом **не фенсится**: `broker.session.timeout.ms` = 9 с, и до потери сессии
дело обычно не доходит. Поэтому отказ выглядит как деградация, а не как падение.

## Что было проверено и исключено

Все три первоначальные гипотезы сняты прямыми измерениями — держать их в голове при
повторной диагностике не нужно:

| Гипотеза | Проверка | Результат |
|---|---|---|
| I/O-столл на PVC Kafka (том из beads y1v) | `dd oflag=dsync` на `/var/lib/kafka/data` против слоя контейнера | 329 мкс против 341 мкс — разницы нет. Том local-path в kind лежит на том же диске VM, отдельного устройства там не появляется |
| Нехватка CPU у VM | PSI на ноде: `cpu some avg10=1.20 full=0`, `io full=0.02`, `memory 0`, steal time 0 | Нода простаивает, таймауты продолжаются |
| Пауза GC в JVM брокера | `kafkaServer-gc.log` | Максимальная пауза ~72 мс, паузы редкие |
| Заблокированный поток контроллера | Три тред-дампа (`kill -3`) с интервалом 20 с | Ни одного `BLOCKED`, все потоки контроллера в `waiting on condition` |

Ключевой довод: таймауты происходят на **полностью простаивающей** машине без пауз GC,
без столлов ввода-вывода и без единого заблокированного потока. Локальный RPC на
`localhost` в такой обстановке не может честно не уложиться в 4.5 секунды.

## Диагностика

Расхождение часов хоста и ноды (быстрая проверка, её же делает `deploy-kind.sh`):

```bash
echo "host: $(date +%s)  node: $(docker exec hybrid-control-plane date +%s)"
```

Поиск самих скачков — сравнение монотонных часов с wall-clock внутри ноды:

```bash
docker exec hybrid-control-plane sh -c \
  'for i in $(seq 1 900); do echo "$(cut -d" " -f1 /proc/uptime) $(date +%s.%N)"; sleep 0.2; done' \
| awk 'NR>1{dm=$1-pm; dw=$2-pw; d=dw-dm; if(d>0.5||d<-0.5) printf "JUMP uptime %.2f delta %.3fs\n", $1, d} {pm=$1; pw=$2}'
```

Здоровый стенд не печатает ни одной строки. Больной печатает пары «вперёд/назад»
примерно раз в 10 секунд.

Проверить, что скачки идут именно от VM, а не от контейнера ноды, — тот же цикл
через `colima ssh --` (для Colima) или в любом другом контейнере.

## Лечение

Часы VM — настройка машины разработчика, а не репозитория, поэтому `deploy-kind.sh`
только предупреждает и ничего не чинит. По возрастанию тяжести:

1. **Перезапустить VM.** Для Colima — `colima stop && colima start`. Снимает расхождение,
   накопленное после сна хоста; стенд при этом переживает рестарт (том Kafka постоянный,
   см. `docs/OVERVIEW.md`).
2. **Проверить синхронизацию времени внутри VM.** `colima ssh -- timedatectl` должен
   показывать `NTPSynchronized=yes`. Признак борьбы двух синхронизаторов — записи
   `journalctl -u systemd-timesyncd` с непоследовательными отметками времени
   («Contacted time server» датировано раньше, чем «Starting ...»).
3. **Не усыплять хост во время работы стенда.** Расхождение накапливается именно на сне.

Поднимать `broker.session.timeout.ms`, чтобы heartbeat перестал истекать, — лечение
симптома: при скачке на 39 секунд не спасёт никакой разумный таймаут, а на здоровой
машине повышенный таймаут только замедлит обнаружение настоящего отказа брокера.

## Чего этот документ НЕ описывает

Обычный холодный старт стенда (первые 1–2 минуты после `deploy-kind.sh` или рестарта
VM) даёт короткий всплеск тех же сообщений `coordinator unavailable`, пока сервисы
поднимаются и группа ребалансируется. Это нормально и проходит само. Тревожно, когда
цикл держится дольше нескольких минут на простаивающей машине — тогда смотри выше.
